# Make Kitchen the canonical owner of Analysis ingestion

Kitchen is the sole runtime owner of canonical Pantry state after Analysis. Counter submits one identified Analysis run over a typed Organization, Repository, or Repository-set scope. Workflow Analysis always runs; the engine-neutral `secret_detection` option requests the independent secret-detection phase. Kitchen performs multi-repository orchestration and produces one canonical result, one atomic Loot batch when credentials are found, and one Pantry reconciliation outcome. Counter never aggregates repository results or mutates graph state locally.

Canonical results carry one terminal outcome for every discovered or explicitly targeted Repository. Workflow Analysis and secret detection independently report `succeeded`, `failed`, `skipped`, or `not_requested`; only `succeeded` grants replacement authority, including for a valid empty result. Each Repository outcome carries `confirmed_present`, `confirmed_gone`, or `unknown` existence evidence, and the explicitly requested Repository or Organization carries equivalent target evidence. Omission, permission failure, and ambiguous not-found responses never authorize deletion. A trustworthy result may have no successful Repository and still be complete; run summaries derive from outcomes rather than a mutable top-level success flag.

Analysis ingestion validates the complete result and reconciles all authoritative scopes through one committed-state replacement. Successful workflow Analysis replaces current Workflow, Job, Vulnerability, workflow-derived Secret reference, Token, self-hosted runner target, and Analysis-owned relationship sets. Successful secret detection independently replaces its Secret evidence set. Confirmed-gone Repository and Organization evidence removes current structure and Analysis evidence without retaining tombstones or hidden placeholders. Runtime, operator, Recon, Loot, History, Agent, Callback, and Session evidence survives. Shared external assets survive while referenced and are removed only when truly orphaned. Failed, skipped, unknown, omitted, and non-requested scopes preserve prior Pantry evidence.

All Analysis-created Assets use `DiscoveredBy = "analysis"`, and replaceable evidence leaves use `analysis_evidence = "workflow"` or `analysis_evidence = "secret_detection"`. Matching shared Assets preserve prior discovery provenance, engagement-owned state, and engagement-owned properties. Explicit per-Asset allowlists replace Analysis-owned properties and relationships, including clearing stale values. Stable evidence identity uses canonical Repository scope plus evidence family and stable source coordinates or an application-computed fingerprint. Detector names remain optional diagnostics and never determine ownership, provider, or identity.

Every request requires a client-generated Analysis ID and Session ID. Once Kitchen validates and registers the run, a Kitchen-owned bounded context continues it despite loss of the synchronous HTTP connection. A reused ID never starts duplicate work: Kitchen returns `409 Conflict` with `analysis_id_conflict` and a recovery `Location`; another Session cannot observe the existing run. Counter permits one active Analysis run, while Kitchen may execute runs from different clients or Sessions concurrently.

The synchronous response and `GET /analyze/result/{id}` return one `AnalysisRun` envelope with independent `analysis`, optional `loot`, and `reconciliation` sections. Each section owns its `status` and optional structured safe error. Analysis reports `pending`, `completed`, or `failed`; partial Repository outcomes still produce `completed` when the result is trustworthy. Loot reports `pending`, `committed`, or `failed` only when credential material was found. Reconciliation reports `pending`, `committed`, or `failed` after Analysis completes. A committed or no-op reconciliation includes the current Pantry revision and no mutation counts. The synchronous endpoint returns HTTP success whenever Analysis completed, even if Loot persistence or reconciliation failed; request validation and failure to produce a trustworthy result remain non-success responses.

Recovery uses the same envelope. Known runs return HTTP success, while unknown, expired, or wrong-Session IDs return `404` without an `unknown` state. Run envelopes remain in a Session-scoped in-memory cache for two hours after their latest state change and do not survive Kitchen restart. Counter polls an ambiguous dropped response from the original start time until the configured Analysis timeout plus one minute, beginning every two seconds and backing off to ten seconds. Three consecutive `404` responses end recovery. After restart or expiry, Counter fetches current Pantry without claiming that the unavailable run produced it.

Credential Loot is durable, self-contained engagement evidence and commits independently before Pantry reconciliation. Kitchen persists all Loot from one Analysis result atomically, continues reconciliation if Loot persistence fails, and reports the distinct sanitized failure. Counter immediately merges committed credentials into its visible Loot stash. Credentials whose persistence failed remain visibly marked as not persisted for the current Counter process so usable access material is not discarded; rerunning Analysis is the persistence retry.

The Counter client exposes one structured Analyze operation and one Analysis-run lookup; the prior standard, deep, ID, and rule-pack method variants are removed. Both operations return the same `AnalysisRun` interface to the TUI. Counter consumes the result for summaries, warnings, history presentation, and credential display, never for Pantry construction. On committed reconciliation it keeps a local snapshot already at or beyond the reported revision or fetches one that qualifies, retaining the previous complete Pantry meanwhile. It makes one immediate attempt and three retries after one, two, and four seconds, each with a ten-second timeout. A valid empty snapshot replaces prior graph state. Exhausted or stale reads leave the previous Pantry visible and tell the Operator which revision committed, which revision remains displayed, and that reconnecting refreshes Pantry. Reconciliation failure leaves Pantry untouched and is displayed separately from Analysis completion; setup offers `r` to rerun the complete Analysis or Enter to continue with the last committed Pantry.

WebSocket Analysis progress is advisory and never establishes a terminal outcome. The phases are `workflow_analysis`, `secret_scan`, and `reconciliation`. Repository metadata sync remains an independent asynchronous follow-up with its own started, completed, and failed notifications. It may update Known Entities and repository access properties after Analysis reconciliation failure, but never imports the failed Analysis evidence. A completed metadata update reports its Pantry revision so Counter can fetch a qualifying snapshot.

Kitchen persists one terminal History record per Analysis ID containing the Analysis summary, Loot status when applicable, reconciliation status, committed Pantry revision, or stable sanitized failure codes. Counter does not create a duplicate terminal record. Arbitrary internal error text is never truncated into a response, diagnostic, History record, or TUI message; allowlisted codes and fixed safe messages cross those interfaces, while Kitchen logs retain safely scrubbed operational detail correlated by Analysis ID.

After Counter accepts a snapshot containing confirmed-gone cleanup, it announces the explicit removed Repository or Organization scopes and states that Loot and History were preserved. Multiple removals use a bounded sample and count. If the selected tree node disappeared, focus moves to its nearest surviving ancestor or the Pantry root while preserving the current pane and scroll position as closely as possible. No modal or confirmation interrupts the Operator.

There is no automatic Analysis or reconciliation replay. Rerunning the original `analyze` or `deep-analyze` command creates a new Analysis ID and fresh evidence. This clean schema 3.0 design removes legacy result normalization, the duplicate Kitchen and Counter importers, the unused Pantry importer, local pruning, old response shapes, the transport-level `deep` flag, and automatic dropped-request resubmission. A generic multi-source provenance framework remains deferred until a second ingestion source demonstrates the need for it. Implementation of this decision is intentionally deferred.
