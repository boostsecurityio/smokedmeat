# Persist Pantry state changes before live publication

Every Kitchen Pantry write is persistence-first. A concrete `CommittedState` module exposes `Update` for ordinary writes and `Replace` for bulk state replacement. Both operations acquire one context-aware writer gate shared by every Pantry mutator, clone the latest committed state, and invoke a callback over an isolated candidate. Readers continue to observe the prior committed Pantry while other writers wait. An unchanged candidate is a successful no-op. A changed candidate is validated and serialized once, then persisted before a short, non-failing replacement of the live Pantry internals. The Pantry pointer remains stable for GraphHub and other consumers.

`Update` computes one final old-to-new granular change set for the durable logical operation. `Replace` emits one committed-state marker and never exposes candidate deltas. Analysis ingestion uses `Replace`; metadata sync, purge, and other ordinary Kitchen writers use `Update`. Publication is ordered after live replacement and before the writer gate opens. Candidate construction emits nothing. Serialization, cancellation before persistence, or persistence failure leaves the previous durable and live Pantry authoritative and emits no publication. Once persistence succeeds, cancellation cannot turn the operation into a reported failure, and no fallible work occurs before live replacement.

A Pantry revision is a durable `uint64` stored in the same serialized Pantry snapshot as its Assets and Relationships. A new empty Pantry begins at revision zero. Each changed durable logical operation advances the revision once regardless of the number of candidate edits or granular changes. No-op and failed operations do not advance it. A Pantry snapshot captures one complete, internally consistent state at one revision so projection never combines values from different revisions.

Pantry observers receive one ordered `OnPantryChange(ChangeSet)` call per committed revision. A typed published change is either `GranularChanges`, containing the final Asset and Relationship changes from one ordinary operation, or `CommittedState`, containing no candidate deltas. GraphHub may batch contiguous granular change sets into a delta carrying both `base_revision` and resulting `revision`. A client applies a delta only when its current revision equals the base, ignores a stale duplicate whose resulting revision is not newer, and requests a snapshot for any other mismatch.

A committed-state marker is a fence. GraphHub cancels and discards pending earlier granular deltas, then sends `snapshot_required` with the minimum committed revision. Clients retain their last complete graph while refreshing, coalesce repeated requests, and accept only a snapshot meeting the newest required revision. Full-mode clients may apply contiguous deltas. Filtered and automatically filtered clients refresh from a Pantry snapshot for every newer change because a granular change can alter subgraph membership. GraphHub obtains every projection from one captured Pantry snapshot.

GraphHub never silently drops an ordered state message. A client whose outbound queue is full is disconnected and recovers by reconnecting to a current snapshot. GraphHub retains no delta replay history, client acknowledgements, or per-client revision state. Reconnects always begin with a snapshot in the requested graph mode.

Kitchen stores Pantry as one JSON value in one BBolt transaction. This matches BBolt's single-writer, multiple-reader, ACID transaction model and keeps the database write short because candidate construction, validation, diff planning, and serialization happen before the transaction. The BBolt adapter atomically replaces supplied bytes and owns no graph behavior. A process failure after durable persistence but before live replacement stops the process; restart loads the durable candidate. The load path must copy BBolt values inside the read transaction before decoding because BBolt byte slices are transaction-scoped.

The whole-snapshot layout is accepted for the current scale, with an explicit large-organization risk. Each changed operation rewrites the complete serialized Pantry, briefly occupies BBolt's single writer, and may increase the database file's high-water size because freed pages are reusable but the file does not automatically shrink. Implementation must record candidate construction, diff planning, validation, serialization, persistence, replacement, and publication timings together with Asset, Relationship, granular-change, and serialized-byte counts. It must include a synthetic large-graph performance test. No arbitrary graph-size rejection or projection cache is introduced until operational evidence justifies one.

This clean persisted contract advances Kitchen directly to schema 3.0 under [ADR-0001](0001-separate-kitchen-schema-version-from-application-releases.md) and requires operators upgrading from schema 2.x to purge existing data. Required verification includes persistence-failure rollback, no publication before persistence, reopen-after-commit with the same revision, old-or-new reader visibility, shared writer-gate participation, stable Pantry pointer identity, one revision per changed logical operation, granular and committed-state ordering, delta-gap recovery, reconnect recovery, race detection, and large-graph performance behavior. Implementation of this decision is intentionally deferred.
